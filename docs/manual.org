* Introduction

ymacs is an Emacs-compatible editing environment built on libyggterm and
implemented in Common Lisp (SBCL/ECL). Its goal is maximum Emacs
compatibility with more surfaces than Emacs ships, configured the modern
way: sane defaults in a shipped literate book (~init.org~), user overrides
in one file (~user.org~).

Design law lives in [[file:spec-primitives.md][spec-primitives.md]]. This manual tracks what is
*implemented*. Chapters carry one of these markers:

- =[parity]= — behaves as Emacs does.
- =[ymacs extension]= — an additive surface Emacs lacks.
- =[divergence #N]= — a deliberate deviation, numbered in
  =docs/emacs-manual/divergences.org=.

* Chapter 1: Installation and Startup =[parity]= [status: implemented]

** Requirements

- SBCL 2.6+ (primary) or ECL 24.5+
- yggterm 3.2+ for libyggterm surfaces (works headless without)

** Build and install

#+begin_src sh
sbcl --load build.lisp
./install.sh
ymacs --version
#+end_src

** Running

#+begin_src sh
ymacs                # open the ymacs surface in yggterm (or headless host)
ymacs file.org       # open file(s) into the daemon
ymacs --eval "(+ 40 2)"
ymacs --config ~/my-init.org
#+end_src

** Daemon and client =[parity with emacsclient]=

The first invocation spawns a daemon (the durable half: buffers, session,
control endpoint). Subsequent invocations are clients that open surfaces
and exit. =ymacs --close= closes this terminal's surface; the daemon
survives, as with emacsclient.

* Chapter 2: Buffers =[parity]= [status: core implemented]

Buffers are rope-backed (piecewise rope, 4k chunks) with value_key
identity for concurrent-edit safety. The full Emacs buffer contract
(names, =*scratch*=, point/mark, modification state, kill-ring) is the
compat target; today: create/open/save/kill, insert/delete, undo,
kill-ring, isearch, folding.

Per the primitives law the buffer's *content model* is an emd document
owned by =emd-renderer=; plain text is the degenerate document. See
Chapter 9.

API: =(make-new-buffer name content)=, =(open-file-buffer path)=,
=(buffer-insert buf pos text)=, =(buffer-delete buf pos len)=,
=(buffer-save buf)=, =(kill-buffer id)=, =(buffer-list)=.

* Chapter 3: Windows and Frames =[ymacs extension]= [status: planned → law]

** Windows =[parity core]=

Windows are tiles over buffers: split horizontally/vertically, balance,
focus. Implemented at tile level; key-driven splitting lands with the
input plane.

** Components — the ymacs window superpower

A window carries a component set chosen by its buffer's major mode and
the window's minor modes: sidebar body, command palette, titlebar
segments, modeline. Buffer-local modes stay buffer-local (as Emacs);
components are window-scoped and additive. Example: org-mode donates a
search box + heading speed-nav to the sidebar; gdb-mode donates
breakpoints/frames; the same buffer in two windows can show different
component sets.

** Frames are yggterm rows =[ymacs extension]=

=C-x 5 2= (=make-frame=) spawns a new yggterm row with its own surface,
attached to the same daemon. Frame parameters map to row properties;
=delete-frame= closes the row. Frames are cheap clients; the daemon owns
state, exactly like emacsclient sessions.

* Chapter 4: Command layer, M-x, and Macros =[parity]= [status: law, recorder bug known]

** Named commands and M-x

Commands are named functions with interactive specs. =M-x= renders in the
command palette (a window component fed by the command layer); completion
is fuzzy. The palette is a *view* — the command layer is what executes.

** Keyboard macros — the macro law

Macros record *command invocations with arguments*, never UI gestures.
Consequences: a macro recorded through M-x replays identically headless
(=ymacs --eval=) with no surfaces at all, and palette UI changes can
never break recorded macros.

Bindings: =C-x (= start, =C-x )= end, =C-x e= execute last,
=name-last-kbd-macro=, =insert-kbd-macro=.

* Chapter 5: Keymaps and Completion =[parity]= [status: keymaps implemented, input plane planned]

Global map + per-mode local maps. Pending prefixes display in which-key.
Default bindings:

| Key     | Command                  |
|---------+--------------------------|
| C-x C-f | find-file                |
| C-x C-s | save-buffer              |
| C-x b   | switch-to-buffer         |
| C-x k   | kill-buffer              |
| C-s     | isearch-forward          |
| M-x     | execute-extended-command |
| C-g     | keyboard-quit            |
| C-/     | undo                     |
| C-y     | yank                     |

Modern completion stack (vertico/consult/orderless/marginalia/corfu) is
the blessed path; ido/helm/ivy/company/linum are discarded with a
diagnostic (divergence #1).

* Chapter 6: Major Modes =[parity]= [status: skeletons]

fundamental, lisp-mode, org-mode, python-mode, c-mode, dired, eshell —
each defines a keymap, syntax table stub, and hook; auto-enabled by
extension.

** Org mode =[ymacs extension]=

Org constructs become typed nodes in the emd document model; ymacs
animates them: =org-cycle= folding, =org-todo= cycling, =org-babel-tangle=,
agenda views. The sidebar gains org search + heading speed-nav when an
org buffer has focus (component law, Chapter 3).

* Chapter 7: Configuration =[divergence #2]= [status: init.org tangle implemented, user.org planned]

ymacs does not ship Emacs's faces. Defaults live in the shipped
~init.org~ literate book; user edits go to =~/.yggterm/ymacs/user.org~
only. Layering is defaults ← overrides (VSCode settings design). Themes
are a small closed token set with a bounded =face→token= shim — face
explosion is impossible by construction.

=M-x settings= opens the dual-window settings system: sidebar = fast
section navigation (Appearance, Editing, Keybindings, Modes, Packages,
About), window = the selected settings document. Changing a setting
writes the override to =user.org=, which stays hand-editable.

* Chapter 8: Surfaces and Transport [status: implemented]

Emacs concepts map to libyggterm surfaces:

| Emacs thing        | ymacs surface                                |
|--------------------+----------------------------------------------|
| frame              | yggterm row (OSC 7717 declare)               |
| window/viewport    | emd document surface (=placement: viewport=) |
| sidebar components | =AppPaneRailBody= contributed pane           |
| echo area          | footer widget                                |
| completions buffer | command palette component                    |

Transport: OSC 7717 declare/heartbeat/close + loopback HTTP control
server (=GET /ping=, =/pane/doc=, =/pane/buffers=, =/pane/which-key=,
=/pane/outline=; =POST /open=, =/action=). Endpoint-ping liveness; stale
URL files are distrusted and respawned.

* Chapter 9: emd-renderer Buffer Ownership =[ymacs extension]= [status: planned]

Buffers are emd documents. The ASCII text surface yedit uses moves into
=emd-renderer= so ymacs, yedit, and future libyggterm apps share one
render/edit engine. emd gains org-mode component extensibility (typed
org nodes; unknown node fails loud). ymacs org mode animates those
components — the same way Emacs org mode gives superpowers to its
renderer.

* Chapter 10: Agent and Headless Access [status: implemented]

#+begin_src sh
ymacs --eval "(buffer-string)"
ymacs --eval "(ymacs-verb-buffers-json)"
#+end_src

Buffer edits carry value_key stability; agents never simulate keystrokes.
See [[file:agent-interaction.md][agent-interaction.md]].

* Chapter 11: ytrace Probes [status: implemented]

In-process probes: =:ymacs-startup=, =:ymacs-buffer-mutation=,
=:ymacs-tile=, =:ymacs-macro=, =:ymacs-elpa=, =:ymacs-control=, and more.
Zero overhead dormant; deterministic when attached.

* Appendix A: Divergence Ledger

Deliberate deviations from Emacs are numbered and tracked in
=docs/emacs-manual/divergences.org= with the Emacs manual node each one
diverges from. The GNU Emacs manuals are vendored (Texinfo sources) under
=docs/emacs-manual/= as the reference base.

Current ledger:

- #1 — Discard ido/helm/ivy/company/linum in favor of the modern
  completion stack.
- #2 — Configuration is init.org defaults + user.org overrides with
  theme tokens, not faces.
- #3 — Frames are yggterm rows, not OS windows.
- #4 — Window components (sidebar, palette, titlebar) are additive
  surfaces Emacs lacks; =display-buffer= splitting remains as parity
  fallback but no ymacs facility requires it.
